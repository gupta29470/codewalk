🔬 Codewalk Review — Architecture & End-to-End Flow

One review engine, three fronts: MCP (host-LLM driven), API (hosted/headless), Frontend (Code Review sidebar). This page is a static reference — open it directly in a browser, no build step.

Component Architecture

Review is built on top of the same codebase-intelligence layer as everything else in Codewalk: a git diff is enriched with graph-derived risk (blast radius, PageRank, cycles, bottlenecks) and stack-aware rubrics before any LLM ever sees it, then batched so the reviewer (human or model) never loses context on a large diff.

🧩 MCP: no LLM call on our side

The host you're already talking to (Claude/Copilot/Cursor) does the actual reviewing. codewalk_run_review only supplies diff + risk + rubric context per batch.

📡 API: server-side, parallel

POST /review runs the batched review with parallel LLM calls server-side and returns raw findings — good for CI hooks or anything outside an IDE session.

🖥️ Frontend: same API, zero curl

The "Code Review" sidebar tab is a UI on top of the exact same API endpoints — diff view, accept/reject per finding, preview diffs, apply with rollback, all clickable.

🕸️ Graph builds on demand

No indexing step required first — the dependency graph builds on-the-fly (~5s) on first review and is cached in .codewalk/graph.duckdb for every mode after that.

MCP Flow — host-LLM driven

Runs inside the AI agent you're already using. Codewalk never calls an LLM itself in this mode — it hands the host model diff + risk + rubric context per batch, and the host reviews and calls tools back to persist findings.

Why no LLM call here

The calling model already has full reasoning capability — duplicating that inside the server would mean a second API key, a second bill, and a worse review (less context than the model already has from the conversation).

Findings persist to disk

Each submit_batch_findings call writes JSON + a hand-readable Markdown companion into the session folder — context window stays clean between batches.

API Flow — hosted, headless

Review as a service: one call runs static analysis + a batched, parallel LLM review server-side and returns structured findings you can act on from any client — CI, a script, or the frontend.

Parallel by batch

Unlike MCP mode's one-batch-at-a-time host loop, the API reviews all batches concurrently server-side since there's no shared conversation context to manage.

Stateless-ish per call

Returns a session_id alongside findings so the same session can be reused for the fix-apply flow (preview-edits / apply-edits) without re-running the review.

Frontend Flow — Code Review sidebar

The web dashboard's left sidebar has a dedicated "Code Review" tab. It's a UI on top of the exact same API — no curl, no agent — with a diff viewer, per-finding accept/reject, a proposed-diff preview, and one-click apply.

Also does single-file review

The same page exposes api.reviewFile(filePath) for reviewing one file in isolation, and api.loadGuidelines(path) to load team guidelines into the rubric context.

requiresIndex: false

The Code Review nav entry doesn't require the full index to be built first — same zero-setup, graph-builds-on-demand behavior as MCP and API mode.

Fix & Apply — safety model

Every mode ends the same way: nothing gets written to disk until a human accepts it, and nothing gets written silently — a preview/dry-run step always comes first, and writes are verified and rolled back on failure.

blocker

Must fix before merge — blocks the PR / verdict is request_changes.

error

Should fix — real bugs, logic errors, security risks.

suggestion

Nice to have — style, naming, minor improvements. Never blocks.

No silent clobbers

A write is refused outright if the target file changed since the preview was generated — stale diffs never get applied on top of newer edits.
